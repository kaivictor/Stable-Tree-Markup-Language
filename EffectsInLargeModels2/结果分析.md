# 大模型对STML、YAML、JSON支持测试的详细结果分析

## 一、测试背景与方法论回顾

### 1.1 测试设计

本次测试使用 `deepseek-v4-flash` 模型，通过两阶段实验评估大模型对三种数据格式（STML、YAML、JSON）的生成与理解能力：

| 阶段 | 内容 | 数据流向 |
|------|------|----------|
| 第一类测试 | 同时生成成对的两种格式 | `generate.py` → `test_data1` → `validityCheck.py` → `test_data2` → `generateSamenessCheck.py` |
| 第二类测试 | 将一种格式翻译为另一种格式 | `translate.py` → `test_data3` → `validityCheck.py` → `test_data4` → `translateSamenessCheck.py` |

### 1.2 关键评估指标

- **有效比例**：能被对应解析器成功解析的文件比例
- **严格匹配比例**：解析后AST完全一致的比例
- **宽松匹配比例**：忽略类型差异（如 `"true"` vs `true`）后AST一致的比例

### 1.3 核心对照组

`yaml↔json` 作为**基准线**——两者均为大模型预训练语料中广泛存在的格式，其匹配率反映大模型在理想条件下的跨格式理解能力上限。

## 二、生成能力深度分析

### 2.1 STML：100%有效率背后的真相

#### 表面数据

| 测试组 | 预期数量 | 有效数量 | 有效比例 |
|--------|----------|----------|----------|
| 第一组（stml&json） | 29 | 29 | **100%** |
| 第三组（stml&yaml） | 29 | 29 | **100%** |
| 第二类（翻译） | 40 | 40 | **100%** |

#### 关键洞察：容错机制掩盖了生成缺陷

根据 [STML规范.md](file:///F:/Studio/Project/my_graduation_project2/Language/STML规范.md) §14（错误恢复与确定性），STML解析器设计原则是**"输入宽松、永不崩溃"**。具体容错行为包括：

| 错误类型 | 解析器行为 | 对用户可见 |
|----------|-----------|-----------|
| 引号未闭合 | 降级为原始标量 | 仅warning |
| 非法映射条目 | 按裸键处理（值为null） | 仅warning |
| 块类型冲突 | 自动恢复并交还父级 | 静默 |
| 多行字符串未闭合 | EOF自动闭合 | 仅warning |
| 内联列表格式错误 | 降级为原始标量 | 仅warning |

这意味着**STML的100%有效率不等于100%语法正确**。通过脚本扫描分析，实际生成质量存在大量问题：

**test_data1（第一类测试）STML问题统计：**

| 未使用引号包裹的键（类YAML风格） | 17/58 | 29.3% | §15 标准输出要求所有键值用双引号包裹 |
| 行尾注释（STML仅支持整行注释） | 20/58 | 34.5% | §4.2 仅支持整行注释 |
| 内联列表格式错误（被容错） | 3/58 | 5.2% | §10 格式错误降级为原始标量 |
| 多行字符串未闭合（被容错） | 5/58 | 8.6% | §11 EOF自动闭合 |
| YAML特定语法混入 | 4/58 | 5.9% | STML不支持锚点/别名/标签 |
| 嵌套内联列表（STML不支持） | 2/58 | 3.4% | §10 仅一层，不支持嵌套 |
| 奇数缩进 | 1/58 | 1.7% | §4.1 缩进仅由空格组成 |

#### 典型错误模式分析

**模式1：YAML风格键名（最普遍）**

大模型生成的STML中大量出现未加引号的键，这是典型的YAML语法习惯迁移：

```stml
# 大模型生成（错误）
姓名: "张三"
年龄: "25"

# STML规范要求（标准输出）
"姓名": "张三"
"年龄": "25"
```

虽然STML解析器对裸键有容错（§9.1：未找到冒号则整行为裸键，值为null），但这会导致**语义完全改变**—— `"姓名": "张三"` 变成了 `"姓名": null` 加上一个裸键 `"张三"`（值也为null）。

**模式2：行尾注释**

```stml
# 大模型生成（错误）
"键": "值"  # 这是注释

# STML规范要求（正确）
"键": "值"
# 这是注释
```

STML §4.2 明确规定仅支持整行注释，行尾注释中的 `#` 及之后内容会被当作值的一部分。

**模式3：多行字符串闭合问题**

```stml
# 大模型生成（错误，缺少闭合或缩进错误）
"多行文本": {
内容行1
内容行2
# 忘记闭合 }

# STML规范要求
"多行文本": {
内容行1
内容行2
}
```

虽然EOF自动闭合（§11）使文件"有效"，但如果大模型在后续继续生成了其他键，这些键会被**吸收进多行字符串内容**，导致结构完全错乱。

### 2.2 JSON：配对格式影响稳定性

| 测试组 | 预期数量 | 有效数量 | 有效比例 | 主要错误类型 |
|--------|----------|----------|----------|-------------|
| 第一组（json&stml） | 29 | 21 | **72.4%** | Extra data（7个）、尾随逗号（1个） |
| 第二组（json&yaml） | 30 | 30 | **100%** | 无 |
| 第二类（翻译） | 40 | 39 | **96.5%** | Extra data（1个） |

**关键发现：与STML配对时JSON质量显著下降**

当要求大模型同时生成JSON和STML时，JSON的有效率仅为72.4%；而同时生成JSON和YAML时，有效率达到100%。这表明：

1. **认知负荷溢出**：STML作为新格式占用了模型的注意力资源，导致JSON生成质量下降
2. **格式混淆**：模型可能在JSON中混入了STML或YAML的语法习惯
3. **上下文污染**：STML的生成提示可能干扰了JSON的生成

**Extra data错误的本质**：大模型在JSON中输出了多个独立对象，未用数组包裹：

```json
// 错误：多个根级对象
{"键1": "值1"}
{"键2": "值2"}

// 正确
[{"键1": "值1"}, {"键2": "值2"}]
// 或合并为一个对象
{"键1": "值1", "键2": "值2"}
```

### 2.3 YAML：相对稳定但仍有瑕疵

| 测试组 | 预期数量 | 有效数量 | 有效比例 |
|--------|----------|----------|----------|
| 第二组（yaml&json） | 30 | 30 | **100%** |
| 第三组（stml&yaml） | 29 | 27 | **93.1%** |
| 第二类（翻译） | 40 | 40 | **100%** |

YAML在stml&yaml配对中出现2个无效文件（93.1%），错误类型为缩进问题和块映射解析失败。这同样反映了**与STML配对时的认知干扰效应**。

## 三、理解能力深度分析

### 3.1 严格匹配结果总览

| 配对方向 | 有效对数 | 严格匹配 | 匹配比例 | 与基准线差距 |
|----------|----------|----------|----------|-------------|
| yaml↔json（基准） | 30 | 12 | **40.0%** | — |
| yaml→json | 20 | 11 | **55.0%** | +15.0% |
| json→yaml | 20 | 8 | **40.0%** | 基准 |
| stml↔yaml | 27 | 3 | **11.1%** | **-28.9%** |
| stml→yaml | 20 | 4 | **20.0%** | **-20.0%** |
| yaml→stml | 20 | 2 | **10.0%** | **-30.0%** |
| stml↔json | 21 | 2 | **9.5%** | **-30.5%** |
| stml→json | 19 | 4 | **21.1%** | **-18.9%** |
| json→stml | 20 | 0 | **0.0%** | **-40.0%** |

### 3.2 基准线分析：yaml↔json = 40~55%

即使对于大模型"熟悉"的格式，跨格式一致性也仅约一半。失败原因按频率排序：

1. **结构重组**（约60%）：键的顺序改变、嵌套层次调整、列表与映射的表示方式差异
2. **类型差异**（约25%）：YAML中 `true` 是布尔值，JSON中 `"true"` 是字符串；数字 vs 字符串数字
3. **多文档处理**（约10%）：YAML多文档与JSON数组/对象的映射方式不一致
4. **空值表示**（约5%）：`null` vs `~` vs 空字符串

### 3.3 STML理解障碍的结构性分析

#### 3.3.1 json→stml：最差的转换方向（0%严格匹配）

这是所有测试中表现最差的方向。通过分析脚本输出，核心问题包括：

**问题A：类型系统冲突**

JSON支持多种原生类型（布尔、数字、null、字符串、数组、对象），而STML §2明确规定：

> "除显式空值外，所有值均为字符串。不存在数字、布尔、日期等自动类型推断。字面量 `true`、`false`、`123`、`1.5` 等全部解析为字符串。"

大模型在json→stml转换中，**未能正确执行类型降级**：

```json
// 源JSON
{"enabled": true, "count": 42, "rate": 3.14}
```

```stml
# 大模型生成（错误：保留了JSON类型语义）
"enabled": true
"count": 42
"rate": 3.14

# STML规范要求（全部应为字符串）
"enabled": "true"
"count": "42"
"rate": "3.14"
```

这解释了为什么**宽松匹配（忽略类型差异）后json→stml从0%跃升至35%**——大量差异确实来自类型未正确字符串化。

**问题B：结构表示方式的根本差异**

JSON使用显式花括号 `{}` 和方括号 `[]` 表示嵌套结构，而STML完全依赖缩进：

```json
// 源JSON
{"outer": {"inner": "value"}, "list": ["a", "b"]}
```

```stml
# 大模型常见错误：保留JSON风格的花括号
"outer": {"inner": "value"}
"list": ["a", "b"]

# STML规范要求
"outer":
  "inner": "value"
"list":
  - "a"
  - "b"
```

脚本检测到4个文件存在"使用花括号表示映射"的问题（如 `stml_json_1.stml`、`stml_json_10.stml` 等）。

**问题C：列表条目语义不理解**

STML §13.2 规定每个序列条目解析为一个Mapping，即使单键也视为含一个键值对的映射。大模型经常生成纯标量列表项：

```stml
# 大模型生成（错误）
- "值1"
- "值2"

# 这在STML中解析为
# [{"": "值1"}, {"": "值2"}]

# 但如果大模型期望的是JSON数组 ["值1", "值2"]
# 语义已经不同
```

#### 3.3.2 stml→json：类型与结构双重障碍（21.1%严格匹配）

此方向的问题与json→stml对称但表现稍好，因为：

1. **类型升级困难**：STML所有值都是字符串，大模型需要判断哪些字符串应转为JSON的布尔/数字/null。模型经常过度推断或推断不足。
2. **多键条目丢失**：STML序列条目可以包含多个键值对（§13.3 兄弟键吸收），大模型可能只提取第一个键值对。
3. **多行字符串处理**：STML多行字符串保留原始格式（包括换行和缩进），大模型在转为JSON时可能错误处理转义。

#### 3.3.3 stml↔yaml：格式混淆最严重（10~20%匹配）

STML和YAML在表面语法上高度相似（都使用缩进、冒号、`-`列表），这反而导致大模型**产生最多的混淆性错误**：

**混淆1：引号规则差异**

| 场景 | YAML | STML |
|------|------|------|
| 键引号 | 可选 | 标准输出要求双引号（输入宽松） |
| 值引号 | 可选 | 标准输出要求双引号（输入宽松） |
| 特殊字符 | 不需要转义（大多情况） | 必须转义 `"` 和 `\n` 等 |

大模型在stml↔yaml转换中，经常将YAML的裸键直接复制到STML中，或将STML的引号键在YAML中保留引号（YAML中 `"键"` 和 `键` 语义相同但影响匹配）。

**混淆2：多行文本表示**

```yaml
# YAML风格（| 保留换行，> 折叠换行）
description: |
  第一行
  第二行
```

```stml
# STML风格（{ } 块）
"description": {
第一行
第二行
}
```

大模型经常在STML中使用YAML的 `|` 或 `>` 语法，或在YAML中错误使用 `{ }` 块。

**混淆3：类型推断差异**

YAML有隐式类型推断（`yes`→布尔，`123`→数字），STML没有。大模型在yaml→stml转换中，有时会将YAML推断出的类型"固化"到STML中（如不加引号的数字），导致STML解析为字符串后与YAML的类型不一致。

### 3.4 宽松匹配的启示

| 配对方向 | 严格匹配 | 宽松匹配 | 提升幅度 | 解读 |
|----------|----------|----------|----------|------|
| yaml→json | 55.0% | 55.0% | 0% | 类型处理已很好，差异主要是结构性的 |
| json→yaml | 40.0% | 45.0% | +5% | 少量类型差异 |
| json→stml | 0.0% | 35.0% | **+35%** | **大量类型未字符串化问题** |
| stml→json | 21.1% | 25.3% | +5.2% | 少量类型推断问题 |
| stml→yaml | 20.0% | 20.0% | 0% | 差异主要是结构性的 |
| yaml→stml | 10.0% | 15.0% | +5% | 少量类型差异 |

**核心结论**：

1. **json→stml的类型降级是大模型最大短板**：35%的匹配率提升空间几乎全部来自未正确将JSON类型转为STML字符串。
2. **stml↔yaml的结构差异是主要障碍**：即使忽略类型，匹配率仍低于20%，说明大模型未能理解两种格式在嵌套结构、列表语义、键值组织上的根本差异。
3. **yaml↔json的类型处理相对成熟**：严格与宽松匹配几乎无差异，说明大模型对这两种已知格式的类型系统有较好把握。

## 四、规范误用的系统性模式

### 4.1 提示词规范（stml_specification.md）的局限性

提供的提示词规范 [stml_specification.md](file:///F:/Studio/Project/my_graduation_project2/Language/EffectsInLargeModels2/stml_specification.md) 是一个**极度简化的教学版本**，与正式规范 [STML规范.md](file:///F:/Studio/Project/my_graduation_project2/Language/STML规范.md) 存在显著差距：

| 规范内容 | 提示词版本 | 正式规范 |
|----------|-----------|----------|
| 错误恢复 | 未提及 | §14 详细定义6种恢复机制 |
| 块类型冻结 | 未提及 | §8 详细定义映射块/序列块冲突恢复 |
| 兄弟键吸收 | 未提及 | §13.3 多键条目核心机制 |
| 复杂序列判定 | 未提及 | §13.4 预扫描机制 |
| 结构冒号算法 | 未提及 | §5 从左到右扫描算法 |
| 引号键模式 | 未提及 | §5.2 非贪婪匹配+紧邻冒号 |
| 空容器约定 | 未提及 | §2 空映射/空序列统一映射为null |

**影响**：提示词仅告诉模型"STML长什么样"，但未告诉它"STML如何容错"。这导致：

1. 模型不知道自己的"小错误"会被解析器静默修复，因此不认为自己生成了错误内容
2. 模型不理解STML的确定性恢复规则，无法预测自己的输出会被如何解析
3. 模型对边缘情况（如引号未闭合、块类型冲突）没有概念

### 4.2 大模型的"YAML惯性"

通过分析50+个存在问题的STML文件，发现大模型表现出强烈的**YAML语法惯性**：

| YAML习惯 | 在STML中的误用频率 | 后果 |
|----------|-------------------|------|
| 裸键（不加引号） | **最高**（~25%文件） | 可能被解析为裸键（值为null），语义完全改变 |
| 行尾注释 | **高**（~20%文件） | 注释内容被当作值的一部分 |
| `|`/`>` 多行文本 | 中 | STML解析器不识别，内容错乱 |
| 锚点/别名（&/*） | 低（~5%文件） | 被当作普通字符，但影响语义匹配 |
| 制表符缩进 | 极低 | 制表符视为普通内容，缩进语义错乱 |

### 4.3 JSON→STML的"结构化思维缺失"

当源格式是JSON（显式括号）时，大模型在转为STML（隐式缩进）时表现出**结构化思维缺失**：

```json
// 源JSON
{
  "users": [
    {"name": "Alice", "age": 30},
    {"name": "Bob", "age": 25}
  ]
}
```

```stml
# 大模型典型错误输出（保留JSON括号思维）
"users": [
  {"name": "Alice", "age": 30},
  {"name": "Bob", "age": 25}
]

# 正确STML
"users":
  - "name": "Alice"
    "age": "30"
  - "name": "Bob"
    "age": "25"
```

脚本检测到多个文件使用花括号 `{}` 表示映射、使用方括号 `[]` 表示列表而非 `-` 条目，这些都是**JSON/YAML结构化语法向STML缩进语法迁移失败**的证据。

## 五、综合结论

### 5.1 核心发现

1. **STML的"100%有效率"是误导性指标**：70.7%（第一类）和62.5%（第二类）的STML文件存在至少一类规范误用，只是被解析器的容错机制掩盖。

2. **大模型处于"语法模仿、语义不懂"的阶段**：
   - 能生成看起来类似STML的缩进结构
   - 但不理解STML的类型系统（全字符串）、列表语义（条目=映射）、多行文本规则
   - 强烈依赖YAML的语法惯性

3. **跨格式理解的瓶颈不在格式本身，而在语义映射**：
   - yaml↔json（已知格式）：40~55%
   - 涉及STML（新格式）：0~21%（严格）
   - 差距：**20~40个百分点**

4. **提示词规范的质量直接影响生成质量**：
   - 当前简化规范遗漏了错误恢复、块类型冻结、兄弟键吸收等核心机制
   - 模型因此无法预判自己的输出会被如何解析

### 5.2 对STML设计的启示

1. **"永不崩溃"的设计目标达成**：§14的容错机制确实确保了任何输入都能解析，但这给评估带来了挑战——"有效"不等于"正确"。

2. **与YAML的表面相似性是双刃剑**：人类和大模型都容易将YAML习惯带入STML，但两者的语义差异（类型系统、列表模型、注释规则）比表面差异大得多。

3. **需要更严格的评估指标**：仅统计"有效比例"不足以评估大模型对STML的掌握程度，应增加：
   - 与标准输出（§15）的相似度
   - 解析器warning的数量和类型
   - 语义一致性（而非仅语法可解析性）

### 5.3 对大模型应用STML的建议

1. **提供完整规范而非简化版**：当前提示词的11条规则不足以让模型理解STML的语义模型，应包含§2数据模型、§8块类型冻结、§13序列规则等核心内容。

2. **强调类型系统差异**：在提示词中明确强调"STML所有值都是字符串，包括数字和布尔值"，并提供正反示例。

3. **提供标准输出示例**：让模型学习 [STML规范.md](file:///F:/Studio/Project/my_graduation_project2/Language/STML规范.md) §15 的标准输出格式，减少YAML风格裸键的出现。

4. **增加 Few-shot 示例**：特别是json→stml的转换示例，展示如何将JSON的显式结构映射到STML的缩进结构。
